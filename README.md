# e164-normalizer

Normalizes **German** phone numbers from structured input (CSV cells, form
fields) to canonical E.164 (`+49…`). The same rules are implemented twice:

- `sql/normalize_phone_de_e164_v1.sql` — a PostgreSQL function, for the database;
- `phone_normalizer.py` — a Python module, for preflight checks and scripts.

Both are checked against one shared set of golden vectors, and against
random inputs, so the database and the scripts give the same answer.

## Why it was built

Contact lists for outbound phone campaigns arrive in every possible notation:
`030 23125 000`, `+49 (30) 23125-000`, `0049 30 23125000`, an extension on its
own, or a number buried in a note. Two problems follow:

1. The same person appears twice in a campaign because the raw strings differ.
2. Scripts and the database disagree on whether a number is usable.

The fix was one explicit rule set with a status and a reason for every input,
enforced in the database and mirrored in Python.

## How it works

Each input gets a result with five fields:

| field | example |
|---|---|
| `phone_canonical` | `+493023125000` or `NULL` |
| `normalization_status` | `valid_de`, `unsupported_country`, `invalid` |
| `country_code` | `49`, `43`, `41` or `NULL` |
| `normalization_reason` | `valid_de_local`, `too_short_de`, `contains_letters`, … |
| `normalization_version` | `de_e164_v1` |

Rules, in order:

1. Empty input → `invalid / empty`.
2. Any letter → `invalid / contains_letters`. Structured fields are not free text.
3. Anything other than digits, `+`, whitespace and `( ) . / -` → `invalid / unsupported_characters`.
4. A `+` that is not the first character, or more than one `+` → `invalid / malformed_plus`.
5. `+49…`, `0049…` and national `0…` become `+49…`; a `0` right after the
   country code is rejected; fewer than 7 digits after `+49` is `too_short_de`.
6. Austria (`+43`/`0043`), Switzerland (`+41`/`0041`) and other international
   numbers are recognised as `unsupported_country`, not thrown away as garbage.
7. Everything else → `invalid / unparseable`.

Python-only helpers (no SQL counterpart): `normalize_phone_loose()` finds a
number inside free text, `is_extension_only()` detects a bare extension
("Durchwahl 42"), `starts_with_local_format()` flags input that had to be
rewritten from national format.

### Example: one contact per list

`sql/example_contacts_unique_by_e164.sql` shows the data-model rule the
normalizer was built for. Raw input is kept as received, a trigger is the only
writer of the normalization columns, and a partial unique index on
`(list_id, phone_canonical)` makes `030 23125 030` and `+49 30 23125 030`
the same contact. Invalid numbers are stored with their reason instead of
being dropped. `sql/example_contacts_unique_by_e164_check.sql` checks this
behaviour inside a transaction that is rolled back.

## Run it

Python (3.10+, standard library only):

```sh
python3 -m unittest discover -s tests -t . -v
```

PostgreSQL (13+, any scratch database). The script installs the function and the
example table, checks the golden vectors, replays 3,000 random inputs generated by
the Python module, and runs the example check:

```sh
DATABASE_URL=postgres://user@localhost:5432/scratch scripts/check_sql.sh
```

Without a local server, for example:

```sh
docker run -d --rm --name pg-e164 -e POSTGRES_PASSWORD=dev -p 5432:5432 postgres:17
DATABASE_URL=postgres://postgres:dev@localhost:5432/postgres scripts/check_sql.sh
```

## Parity

`sql/golden_vectors_check.sql` takes any vector file in the format of
`tests/golden_vectors.de_e164_v1.json`. `scripts/fuzz_vectors.py` writes such
a file from random inputs, with the Python result as the expected value, so a
passing run means SQL and Python agree on those inputs.

Character classes are spelled out in ASCII in both implementations. Locale-aware
classes such as `[[:alpha:]]`, `[[:space:]]` or Python's `str.isalpha()` behave
differently for non-ASCII input (for example a non-breaking space). With the
explicit classes, such input is `unsupported_characters` on both sides.
Whitespace means the ASCII set space, TAB, LF, CR, FF and VT. In SQL the
vertical tab is written `\x0b`, because `\v` is not in PostgreSQL's documented
list of string escapes. The golden vectors and the random inputs include
vertical tabs and the letters used in escape sequences (`b f n r t v x`).

## Test numbers

All German numbers in this repository come from the ranges the
Bundesnetzagentur provides for media use ("Drama Numbers", e.g.
`030 23125 000–999`):
<https://www.bundesnetzagentur.de/DE/Fachthemen/Telekommunikation/Nummerierung/DramaNumbers/artikel.html>.
Austrian, Swiss and other international examples use all-zero subscriber
parts, which are invalid by design. The random inputs from
`scripts/fuzz_vectors.py` are never stored in the repository.

## Limitations

- German numbers only. This is not a general international validator.
- Length checks are minimal (at least 7 digits after `+49`). The normalizer
  does not check area codes or whether a number is assigned.
- `normalize_phone_loose()` is a heuristic for free text and can miss numbers
  or pick the wrong one.
- Not packaged for PyPI. Copy the module or the SQL file.
